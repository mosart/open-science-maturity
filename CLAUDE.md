# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A self-assessment tool for Open Science infrastructures, currently offering two assessment frameworks: the [Principles of Open Scholarly Infrastructure (POSI) v2.0](https://openscholarlyinfrastructure.org/) and a draft SPII v0.0.1 framework. It is a single standalone `index.html` file — there is no build step, package manager, server, or committed test suite. Styling comes from the [Oat](https://oat.ink) CSS framework (vendored locally as `oat.min.css`) layered with color/font tokens hand-copied from the [SURF Design System](https://surfnet.github.io/DesignSystem/).

## Running / previewing

Just open `index.html` directly in a browser (or serve the directory with any static file server). There is nothing to install or build.

## Architecture

Everything lives in `index.html`: markup, inline `<style>`, and inline `<script>`. There is no JS framework — all rendering and interactivity is vanilla DOM manipulation, driven by a single in-memory `state` object.

**Data model** (`<script id="app-logic">` in `<head>`): `FRAMEWORKS` is the list of *built-in* assessment frameworks, each with a `title`/`description`/`aboutHtml`, optional `draft` flag, and a `sections` array. There are two entries: POSI v2.0 (`id: "posi"`, `draft` unset, 3 sections — Governance, Sustainability, Insurance — 20 principles total; raw content in the `POSI` constant, referenced by `FRAMEWORKS[0].sections`) and SPII v0.0.1 (`id: "spii"`, `draft: true`, 5 sections — Openness, Autonomy, Sustainability, Interoperability, Researcher-centric — 19 principles total; raw content in the `SPII` constant, referenced by `FRAMEWORKS[1].sections`). Each principle has a stable `id`, `title`, verbatim `text` (transcribed from openscholarlyinfrastructure.org for POSI), and may optionally carry `criteria` (an object with `{compliant, progress, "non-compliant"}` keys holding short rubric text shown per status card) and `improvementAction` (text shown as a "To improve:" note) — absent for POSI, present on every SPII principle, rendered only when present so a framework can opt into richer guidance without affecting others. Beyond the built-ins, `state.customFrameworks` holds framework objects a user has imported at runtime (same shape as `FRAMEWORKS` entries); `<script id="app-render">`'s `all_frameworks()` (`FRAMEWORKS.concat(state.customFrameworks)`) is what rendering code iterates wherever custom frameworks should show up (tabs, sidebar nav, summaries, badge) — a handful of call sites that intentionally still use bare `FRAMEWORKS` (the `initial_state()` build, the default `activeFrameworkId`, and `merge_loaded_state`'s id-collision check) stay built-ins-only on purpose. `validate_framework_shape(obj)` is the shared structural check (id/title/sections[].section/sections[].principles[].id·title·text) used both when importing a framework at runtime and when reloading a previously-exported report that included `customFrameworks`; `framework_state_slice(framework)` builds the `{principleId: {status: null, notes: ""}}` slice for a framework, shared by `initial_state()` and by custom-framework import/reload. `ACTIVITIES` is `{primary, related}` — two named, boxed groups for the "Classify" picker ("Research life cycle activities" and "Research related activities"), 12 items total. `ICONS` holds the three inline SVG status icons; `ACTIVITY_ICONS` holds one inline SVG per classification item (keyed by the item's exact label), rendered via the shared `activity_icon_markup(item, size, strokeColor, extraAttrs)` helper — next to each Classify checkbox (`currentColor`, tinted via the `.activity-icon` CSS class) and, for whichever items are selected, as a row of small icons in the assessment badge (`#333333`, positioned with explicit `x`/`y` since that markup is a standalone exported SVG with no CSS context). `initial_state()` builds a fresh `state` object: `{name, description, url, assessedOn, activities, customFrameworks, frameworks: {[frameworkId]: {[principleId]: {status, notes}}}}`, where `status` is `"compliant"`, `"progress"`, `"non-compliant"`, or `null`, and `assessedOn` defaults to today's date (`today_iso_date()`). `compute_summary(state, frameworkId)`, `build_export_object(state)`, `merge_loaded_state(loaded)`, `validate_framework_shape(obj)`, `framework_state_slice(framework)`, and `ring_segment_offsets(radius, count)` are pure functions with no DOM access — this is what makes them testable outside a browser (see Testing below).

**Rendering** (`<script id="app-render">` in `<body>`): `render()` rebuilds `#app` entirely from the global `state` — the header (intro paragraph + "About this tool" and "Changelog" accordions) and `render_tabs()`, which wraps everything else in a hand-rolled tab strip: one tab for "OS Infrastructure Description" (name/description/URL/assessment-date fields, plus "Classify" as a sub-heading with two boxed activity columns using Oat's `.row`/`.col-6` grid) and one tab per `all_frameworks()` entry (title, optional draft `role="alert"` banner, description, "About `<framework>`" accordion, framework-level summary with scoped id `summary-heading-<frameworkId>`, each content sub-section's DOM id generated by `section_id(frameworkId, section)` — a slugified section name scoped to its owning framework, not hardcoded, so id collisions can't occur even if two frameworks reuse a section name — then one `<details id="principle-<frameworkId>-<principleId>" data-principle-id="..." data-framework-id="<frameworkId>">` per principle — 3 status cards with icons + a notes `<textarea>`). Tabs use plain `role="tablist"`/`role="tab"`/`role="tabpanel"` markup (styled by `oat.min.css`, which ships the CSS for Oat's `<ot-tabs>` pattern but not its JS) with `switch_tab(tabId)` handling the `aria-selected`/`hidden` toggling by hand — there's no new dependency, and no `<ot-tabs>` custom element to register. `activeTabId`/`activeFrameworkId` are both module-level (not persisted in exported JSON); switching to a framework's tab also sets `activeFrameworkId` and calls `update_badge()`, so the assessment badge always reflects whichever framework tab was last viewed. `navigate_to(tabId, anchorId)` is the single place that switches tabs, force-opens a `<details>` target, and scrolls to it — used by every sidebar nav link (framework, section, and per-principle) and by the "About"/"Changelog" links (`tabId: null`, since those live in the page header above the tabs, not in a tabpanel). `render_sidebar_nav()` now goes one level deeper than framework → section: each section also lists its principles individually via `render_principle_nav_link`, each with a `.nav-status-dot[data-status]` colored by that principle's current status (compliant/progress/non-compliant/unanswered); `update_principle_dot(frameworkId, principleId, status)` — called from `set_status()` — updates a dot in place without a full re-render. A framework's nav group defaults open when `!framework.draft` and collapsed when `draft: true`. The sidebar footer (`render_sidebar_footer`: just the assessment badge + hovercard and the badge SVG/PNG download buttons) is rebuilt on every `render()` too; the page's title, mobile nav toggle, and Import/Export menus live in a static `nav[data-topnav]` in the body (never rebuilt by `render()` — its buttons are wired once, at the bottom of the script, alongside the other delegated listeners). Interaction handlers (`set_status`, `toggle_activity`, the notes/field input listeners) mutate `state` directly and call the narrower `update_summary()` (which also refreshes each tab's live "(scored/total)" label via `tab_label_text`) /`update_badge()` rather than a full `render()`, so typing in a field doesn't lose focus. `render()` itself is called on first load, after a JSON report is loaded (`load_json`), and after a custom framework is successfully imported (`import_custom_frameworks`), since those are the only times the whole DOM tree needs rebuilding from a new `state`.

**When adding a new POSI principle or activity**: add it to the `POSI`/`ACTIVITIES` data in `<script id="app-logic">` — the UI, scoring, JSON export/reload, and badge all render from that data automatically. Don't hand-edit the generated `<details>` markup; it's rebuilt by `render()` on every load.

**Top bar** (`nav[data-topnav]`, static markup in `<body>`, never rebuilt): the app title, the mobile sidebar toggle, and two menus built from Oat's `<ot-dropdown>` pattern (a plain wrapper tag — no custom-element JS — around a `popovertarget` button and a native `[popover]` panel; `oat.min.css` styles both scoped under `ot-dropdown`). **Import**: "Import Assessment Report (JSON)" (`load_json`, via a hidden file input), "Import Assessment Framework (JSON)" (`load_custom_frameworks` → `import_custom_frameworks`, same file-input pattern), "Download Assessment Framework Template (JSON)" (`download_framework_template`, downloads the static `FRAMEWORK_TEMPLATE` object as a starting point for authoring a custom framework). **Export**: "Export Assessment Report (JSON)" (`download_json`), "Print Assessment Report (PDF)" (`download_pdf`), "Download Assessment Frameworks (JSON)" (`download_custom_frameworks`, exports `state.customFrameworks` — the built-ins aren't included since they already ship with the app).

**Custom framework import**: `import_custom_frameworks(frameworks)` accepts an array (a re-imported "Download Assessment Frameworks" export, or a single-item array from the template/a hand-authored file); each entry is checked with `validate_framework_shape` and against every existing framework id (built-in and already-imported) via `all_frameworks()`, added to `state.customFrameworks` plus a fresh `state.frameworks[id]` slice via `framework_state_slice` if valid and non-colliding, then `render()` runs once if anything was added. Invalid or colliding entries are reported via a single `alert()` listing what was skipped, without blocking the entries that did succeed. `build_export_object`/`merge_loaded_state` round-trip `state.customFrameworks` (plus their scores) the same way they already round-trip the built-ins, so a custom framework you're partway through scoring survives an Export/Import Assessment Report cycle.

**Export flows**:
- `download_json_blob(data, filename)` is the shared JSON-blob-download helper (`JSON.stringify` → `Blob` → `trigger_download`); `download_json()`, `download_framework_template()`, and `download_custom_frameworks()` are all thin wrappers over it.
- `download_pdf()` renders `document.body` via `jsPDF` (loaded from a CDN, `doc.html()`) into `report.pdf`. Because `doc.html()` renders via html2canvas using the page's on-screen computed styles, it does not fire `beforeprint`/honor `@media print`, so `download_pdf()` does its own force-open of every `<details>`, temporarily un-hides every `[role="tabpanel"]` (so all frameworks' content is captured regardless of which tab was active), and toggles a plain `body.printing` class (mirrored by a non-media-query CSS rule) to hide the top bar, the sidebar footer's buttons, and unselected status cards — restoring the original `<details>` open/closed and tabpanel `hidden` state once the PDF is saved. The browser's own print preview (Ctrl/Cmd+P) instead uses the `@media print` rules directly, with `beforeprint`/`afterprint` listeners doing the same force-open/un-hide-tabpanels/restore dance.
- `build_badge_svg_markup(state)` builds a self-contained `<svg>` (using the title from the active framework, concentric rings computed via `ring_config_for(framework)` — one per section, each split into one arc per principle via `ring_segment_offsets` — the overall `%`, infrastructure name, a row of the selected activities' icons via `selected_activity_items(state)` + `activity_icon_markup`, and the assessment date) — deliberately compact; the full per-section breakdown lives in `build_badge_hovercard_html(state)`, shown as a `.hovercard` on hover/focus of the badge (plain CSS, no new dependency). `download_badge_svg()`/`download_badge_png()` export the compact badge as a static image the infrastructure can host on its own site; there is no live/dynamic embed since the tool has no backend.

**Styling**: color and font tokens are hand-copied from the [SURF Design System](https://surfnet.github.io/DesignSystem/) as CSS custom properties (`--primary`, `--warning`, `--destructive`, `--compliant`, `--font-sans`) in `:root`, with dark-mode overrides under `@media (prefers-color-scheme: dark)`. This is a copy of token *values*, not a dependency on SURF's packages — the page has no new runtime dependency beyond the pre-existing jsPDF/html2canvas CDN scripts. Beyond those tokens, layout and typography lean on Oat's own system rather than reimplementing it: the custom `<style>` block only overrides what Oat doesn't already provide, and otherwise sizes/spaces things with Oat's own `--text-N`/`--space-N` custom properties and its `.row`/`.col-N` grid (status cards, the Classify columns, and the URL/date field pair all use `.row` + `.card`/`col-N` rather than ad-hoc flexbox, so they get Oat's built-in mobile stacking at 768px for free). `#app` is capped at `var(--container-max)` and centered so content doesn't stretch edge-to-edge on wide screens. `[role="tabpanel"]` gets a `.card`-like background/border/padding so each tab reads as a distinct boxed panel; `[role="tab"]`/`[role="tablist"]` rely entirely on Oat's own styling. `.nav-status-dot[data-status]` colors the per-principle sidebar dots from the same `--compliant`/`--warning`/`--destructive` tokens the status cards use, defaulting to `--border` (grey) when unanswered.

## Testing

There is no committed test suite — this matches the project's "no build step" philosophy. The pure functions in `<script id="app-logic">` (`compute_summary`, `build_export_object`, `merge_loaded_state`, `validate_framework_shape`, `framework_state_slice`, `ring_segment_offsets`) have no DOM dependency and can be exercised from Node by extracting that script block's text (regex on `<script id="app-logic">...</script>`) and running it in a `vm.createContext`, if you need to verify logic changes without a browser. Everything else (rendering, interactivity, PDF, badge image export) is verified manually by opening `index.html` in a browser.

## Notes

- A framework's `draft: true` flag (on a `FRAMEWORKS` entry, built-in or custom) renders as a `role="alert" data-variant="warning"` banner (styled by `oat.min.css`) at the top of that framework's tabpanel, and as a "(draft)" suffix in its sidebar navigation link; this allows frameworks to be marked as unfinished individually. POSI has no `draft` field, so it shows no banner; SPII sets `draft: true`, so its banner appears.
- The linked `jspdf` and `html2canvas` scripts are pulled from `unpkg.com` / `html2canvas.hertzen.com` CDNs — there is no local vendoring for these two.
- The app's title now appears exactly once, in the static top bar's `<strong>` — there is no separate sidebar heading or main-content `<h1>` any more.
